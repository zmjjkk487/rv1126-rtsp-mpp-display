📖 Lesson 3：ONVIF 协议栈与你的代码

目标：你已经实现了 ONVIF 客户端（发现 + 取流），这课把**每一段代码**对应到**协议规范**，让你知道自己在跟什么打交道。

一、ONVIF 是三层协议栈

🔍 第 1 层: WS-Discovery (发现层) — 找到摄像头
   UDP 组播 239.255.255.250:3702
   ⬇ 对应你的代码: onvif_disco.c

📨 第 2 层: SOAP/XML (消息层) — 怎么说话
   HTTP POST + XML Envelope
   ⬇ 对应你的代码: onvif_soap.c 的 soap_post()

📦 第 3 层: ONVIF 服务模型 (业务层) — 说什么话
   Device 服务 / Media 服务 / PTZ 服务 ...
   ⬇ 对应你的代码: GetProfiles / GetStreamUri 函数

二、第 1 层：WS-Discovery — 你发的那条 UDP

你代码里 PROBE_XML 模板（onvif_disco.c）有三个关键 Header 字段：

字段作用你代码里
w:MessageID本条探针的唯一 ID，摄像头回复时带回来（RelatesTo），用于匹配请求/响应make_uuid() 生成
w:To协议版本标识（2009 版 discovery 的 URN），不是地址写死的 URN
w:Action声明"这是一条 Probe 消息"写死的 URI
💡 为什么摄像头回包里有 RelatesTo？ 因为 UDP 是无连接的——没有"你回我"的通道。靠 MessageID/RelatesTo 配对。这就是协议层解决"UDP 怎么知道是谁回的"的方法。

回复里的关键字段

字段含义你的解析
d:XAddrs摄像头的服务地址列表（空格分隔）xml_extract() 提取第一个
d:Scopes设备信息（类型/位置/型号），URL 编码提取作显示用
d:Types设备类型（NetworkVideoTransmitter 等）提取作过滤

三、第 2 层：SOAP — 你拼的那段 XML

你代码里每次请求都是一个 Envelope（信封）：

<s:Envelope xmlns:s="http://www.w3.org/2003/05/soap-envelope">
  <s:Header>...</s:Header>   <!-- 元信息: 认证、路由 -->
  <s:Body>
    <trt:GetProfiles/>       <!-- 业务请求 -->
  </s:Body>
</s:Envelope>

namespace 前缀为什么这么多？

每个前缀绑定一个 XML 命名空间 URL：

前缀命名空间含义
s:.../2003/05/soap-envelopeSOAP 信封结构（Header/Body）
trt:.../ver10/media/wsdlONVIF Media 服务
tt:.../ver10/schemaONVIF 通用数据类型
wsse:.../wssecurity-secext-1.0.xsdWS-Security 认证
💡 为什么搞这么复杂？ 因为不同厂商可能在同一份 XML 里用相同的标签名（比如各自的 Uri），命名空间就是"姓氏"，区分谁家的。这也是为什么你代码里的 xml_tag_parse() 要支持 tt:Uri 和 Uri 两种形式。

SOAPAction 是干嘛的？

HTTP 头里 SOAPAction: http://www.onvif.org/ver10/media/wsdl/GetProfiles —— 告诉服务器"这次请求要调用哪个操作"，服务器可以据此路由，不用解析整个 XML。

四、第 3 层：服务模型 — 你调的那两个操作

Device 服务 (device_service)         Media 服务 (Media / media_service)
  GetCapabilities ──> 拿到 Media 地址       GetProfiles ──> 拿到所有码流配置(token)
  GetDeviceInformation                     GetStreamUri ──> 拿到 RTSP URL
  (重启/改用户/云台等)                        (分辨率/码率等)

你的代码只用了 Media 服务的 GetProfiles 和 GetStreamUri，但注意一个事实：

实际经验 你把 GetProfiles 直接发到了 device_service 也成功了 —— 因为很多摄像头（包括海康）把所有服务挂在同一个 URL 上，只靠 SOAPAction 区分。规范的流程是：先 GetCapabilities 找到 Media 服务地址，再发 Media 请求。你的代码先试 device_service、失败再试 /onvif/Media、/onvif/ptz_service——这是"宽容实现"的工程智慧。

五、动手回顾：你在板上做过的事

你还记得这些命令吗？它们就是协议在现实中的样子：

# 1. 发现阶段: ffprobe 直接探测摄像头 ONVIF 服务
curl -s http://192.168.50.168/onvif/device_service

# 2. SOAP 请求: 带认证的 GetProfiles (你验证过返回 MainStream/SubStream)
curl -u admin:123456 -X POST http://192.168.50.168/onvif/device_service \
  -H 'Content-Type: application/soap+xml' \
  -H 'SOAPAction: "http://www.onvif.org/ver10/media/wsdl/GetProfiles"' \
  -d '<s:Envelope ...><s:Body><trt:GetProfiles/></s:Body></s:Envelope>'

在板上重新执行一次，对照本课内容，你就能看到：SOAPAction 路由、命名空间、Envelope 结构——都在眼前。
