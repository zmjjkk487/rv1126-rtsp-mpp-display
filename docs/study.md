## 0. 学习方法论讨论

### 0.1 讨论背景

**你的提问**：作为嵌入式音视频开发实习生，当前项目几乎完全依赖 AI 完成，感觉在 AI 时代已经没有学习的必要，感到迷茫。这种情况下的学习意义在哪里？

**我的回答**：

你现在的处境和接下来的情形：

> 现在（实习生） → 3 个月后 → 1 年后
> AI 帮你写了整个项目 → 板子换了，屏幕换了，摄像头协议变了 → 你要面另一家公司的嵌入式音视频岗位
>                                       AI 改不动了

**场景 1**：板子换了。老板扔给你一块 RK3588，Ubuntu 系统，没有 RGA，用的是 DRM 不是 fbdev。AI 能写但前提是**你知道要告诉 AI 什么**。

**场景 2**：现场出问题了。摄像头画面花屏，不是代码崩溃，是画面上有绿色条纹。AI 看不到你的屏幕，不知道花屏长什么样。但如果你学过 NV12 颜色空间，你会立刻判断：**这是 stride 对齐问题**。

**场景 3**：面试。面试官问你延迟瓶颈在哪，你没学过就只能说"我们用了 GStreamer 管道"。学过的人会说"主要瓶颈是 rtspsrc 的 jitterbuffer，latency 设了 300ms，理论上可以降到 100ms 以内，但实际测试 UDP 丢包率高"。

**核心结论**：**AI 能替你写代码，但不能替你承担责任。** 学习的意义就是让自己有资格承担那份责任——因为总有一天，问题会超出 AI 的能力边界，而那时候必须有人知道该怎么办。

### 0.2 "不要学代码，要学数据流"


**你的提问**：为什么强调"不要学代码，要学数据流"？这种方式与传统逐行学习代码有什么区别？

**我的回答**：

不要学"代码"，要学"数据流"。你不需要记住 `g_object_set` 有几个参数。你要学的是**这个项目里，数据是怎么流动的**。因为在嵌入式音视频领域，所有问题最终都归结为一句话：**"数据在哪一步坏了？"**

**自测方法**：打开项目的每一个 `.c` 文件，每一行代码，问自己："这行为什么这么写？删掉会怎样？有没有别的写法？"能回答上来的跳过，回答不上来的就是你要学的。

举例——你的 `main.c` 里有一行：

```c
g_object_set(G_OBJECT(rtspsrc), "protocols", 4, NULL);
```

- `4` 这个数字是什么意思？为什么是 4 不是 3？
- 如果把 4 删掉，在什么情况下程序还能跑，什么情况下会挂？
- 你怎么验证它真的生效了？

想不出来就是问题——这行代码是 AI 写的，但如果摄像头突然连不上了，你必须知道答案。

### 0.3 教学方式约定（三层结构）

**你的要求**：以后让你解释的时候不要一看见项目就把概念只对我的项目解释，让我误以为某个概念只能是我的这个项目格式。

## 1. 模块 0：摄像头内部（光 → H.264 → RTP 分包）

### 1.1 摄像头 = 三块板

**你的确认**：根据了解，网络摄像头出厂时通常包含三块电路板（传感器板、主控板、接口板），我的理解是否正确？

**确认**：对！

| 板子 | 作用 |
|------|------|
| 传感器板 | 镜头 + CMOS 感光芯片，光→电，输出 Bayer RAW |
| 主控板 | 嵌入式 SoC（海思 Hi3516 等），含 ISP + H.264 编码器 + Linux 跑 RTSP 服务 |
| 接口板 | 电源、网口 RJ45、PoE 供电、SD 卡槽、报警 IO |

你的项目只跟主控板的 RTSP 服务 + 编码器输出打交道。

---

### 1.2 从光到 Bayer RAW：感光芯片怎么"看"颜色

**概念**：CMOS 每个小格子物理学上只能感应**光的强度**（光强→电流→ADC→0~255 的值），不能感应光的颜色。

**Bayer 滤镜**：芯片上盖了一层微型彩色滤镜，每个格子上盖一种颜色：

```
第 1 行： 红滤镜  绿滤镜  红滤镜  绿滤镜  红滤镜  绿滤镜 ...
第 2 行： 绿滤镜  蓝滤镜  绿滤镜  蓝滤镜  绿滤镜  蓝滤镜 ...
第 3 行： 红滤镜  绿滤镜  红滤镜  绿滤镜  ...
第 4 行： 绿滤镜  蓝滤镜  绿滤镜  蓝滤镜  ...

50% 绿色（人眼对绿色光最敏感）+ 25% 红 + 25% 蓝
```

此时每个格子只有一个颜色值（R 或 G 或 B），不是完整的 RGB。这叫 **Bayer RAW 数据**。

**你的回答**（回答我的提问"摄像头怎么知道颜色"）：通过像素坐标化。

**纠正**：坐标只能告诉你"第几行第几列"，不能告诉你颜色。真正区分颜色的是每个格子上面的**微型彩色滤镜**。

---

### 1.3 ISP 处理：去马赛克（demosaicing）

**概念**：用周围像素的颜色值取平均，猜出每个像素缺失的另外两种颜色。

```
红滤镜下的像素，缺失 G 和 B：
  G = 上下左右四个绿色邻居的平均值
  B = 四个对角线蓝色邻居的平均值

绿滤镜下的像素，缺失 R 和 B：
  R = 左右两个红色邻居的平均值
  B = 上下两个蓝色邻居的平均值
```

**你的测试回答**（我问"红点补 G 用哪个方向"）：上下左右的绿色邻居。✅ 正确。

ISP 还做：白平衡、曝光调整、降噪、锐化。

输出：704×576 个完整的 RGB 像素，约 **1.2MB/帧**。

---

### 1.4 为什么 RGB 转 YUV

**你的追问**：RGB 转换到 YUV 的目的难道不是为了降低数据量吗？

**纠正**：**RGB→YUV 转换本身不省空间。** 转换后还是 3 字节/像素，大小一模一样。它只是换了个表示法。

**真正省空间的是后面的色度降采样**。RGB→YUV 的意义是把**亮度**和**颜色**拆开：

```
RGB 里：每个通道都混合了亮度+颜色信息，R=200 你分不清是"很亮的红"还是"不太亮的浅红"
YUV 里：Y 只负责亮不亮，U/V 只负责什么颜色，完全分开
```

分开之后才能对人眼不敏感的颜色做降采样。

**为什么 RGB 不能直接降采样？** 因为 RGB 三个通道都混着亮度信息。如果你把 R 通道降采样，画面会直接变暗变红，肉眼一眼看出来。YUV 把亮度全集中在 Y 通道，U 和 V 纯粹管颜色——丢掉一半 UV 只影响颜色精细度，不影响亮度，人眼看不出。

**转换公式（BT.601）**：

```
Y = 0.299×R + 0.587×G + 0.114×B（亮度，绿色权重最大）
U = -0.169×R - 0.331×G + 0.500×B（蓝色色度）
V = 0.500×R - 0.419×G - 0.081×B（红色色度）
```

这就是 `fbdev.c` 里手写的 `nv12_to_rgb888` 函数的逆运算。

---

### 1.5 色度降采样（4:2:0）→ NV12

**概念**：人眼对亮度敏感、对颜色迟钝。利用这个缺陷：每个像素保留 Y（亮度），但每 4 个像素共用一个 U 和一个 V。

```
YUV 4:4:4（没省）：  Y Y Y Y   U U U U   V V V V   → 1.2MB
YUV 4:2:0（NV12）：  Y Y Y Y   U   U     V   V     → 600KB（省一半）
```

**NV12 内存布局**：

```
[Y₀ Y₁ Y₂ Y₃ ... Y₄₀₅₅₀₃] [U₀ V₀ U₁ V₁ ... U₁₀₁₃₇₅ V₁₀₁₃₇₅]
 ←—— 704×576 = 405,504 字节 ——→  ←—— 352×288×2 = 202,752 字节 ——→

总大小 = 608,256 字节 ≈ 600KB
```

**名字含义**：NV12 = NVidia 12 = YUV 4:2:0 Semi-Planar。`420` = 4:2:0 色度采样，`SP` = Semi-Planar（Y 一个平面，UV 交错一个平面）。代码里 `RK_FORMAT_YCbCr_420_SP` 就是 NV12。

**空间节省链路总结**：

```
RGB (1.2MB/帧) → ①RGB→YUV 转换（不省大小，只是亮色分离）
                   → ②色度降采样 NV12（600KB，省一半）✅
                       → ③H.264 压缩（8KB/帧，再省 75 倍）✅
```

### 1.6 H.264 压缩

#### 1.6.1 为什么要压缩

NV12 600KB × 15fps = 9MB/s。百兆网口理论 12.5MB/s，看似够但实际有协议开销 + 其他设备共享带宽。且存储和传输都要尽可能小。

#### 1.6.2 两个核心思想

**空间压缩（帧内）**：一张图里天空区域相邻像素几乎一样，没必要每个都精确记录。切成 16×16 宏块，每块独立压缩。

**时间压缩（帧间）**：相邻两帧，大部分东西没动。不需要传整个第 2 帧，只需告诉解码器"第 2 帧 = 第 1 帧 + 把车往右移 5 像素"。

#### 1.6.3 I 帧和 P 帧

**I 帧（IDR，关键帧）**：完整压缩画面，不依赖任何其他帧。≈15-30KB。

**P 帧（预测帧）**：只记录和上一帧的差异。≈2-8KB。

**你的疑问（关于 GOP 和帧率的关系）**：如果视频帧率为 60fps、GOP 设为 15，是否意味着两个 I 帧之间存在 60 个 P 帧？

**纠正**：**不是。** GOP 指的是总帧数（含 1 个 I），不是帧率：

```
GOP=15：每 15 帧一个组，含 1 个 I + 14 个 P
15fps 下 → 每隔 1 秒一个 I 帧
60fps 下 → 每隔 0.25 秒一个 I 帧

让 60fps 也是每秒一个 I 帧 → GOP 要设成 60（I + 59 个 P）
```

**P 帧的依赖链**：

```
P1 依赖 I0 → P2 依赖 P1 → P3 依赖 P2 → ...
P3 丢了 → P4~P14 全部无法解码 → 画面卡住 → 等下一个 I 帧恢复
```

这就是 `latency=300` 缓冲的意义——给丢包留出重传时间。

#### 1.6.4 H.264 编码器内部（只需知道存在，不需要深入）

编码器对每个 16×16 宏块做四步：预测（帧内 9 种模式、帧间运动搜索）→ DCT 变换（像素→频率）→ 量化（抹掉高频细节，这一步损失画质，不可逆）→ 熵编码（常见值用短码）。

**你的确认（关于学习深度）**：对于 H.264 编码器内部的 DCT/量化/熵编码算法细节，是否需要在当前阶段深入学习？如果职业目标是月薪 15k 以上的嵌入式音视频开发岗位，这些底层算法知识是否是必需的？

**回答**：**不需要。** DCT 变换矩阵、量化推导、预测模式——这些是编解码器芯片设计者学的。你真正需要的是 H.264 的**接口层面**（NAL、SPS/PPS、I/P 帧、GOP），不是算法内部的数学推导。面试会问工程问题（延迟瓶颈、NV12 大小、info_change 流程），不会问你怎么算 DCT。

### 1.7 NAL 单元（H.264 的最小组织单位）

#### 1.7.1 通用概念

**NAL（Network Abstraction Layer，网络抽象层）**= H.264 码流的最小组织单位。

```
一个 NAL 单元 = NAL 头（1 字节）+ 载荷数据。

[NAL头 (1字节)] [载荷数据...]
     ↑
  低 5 位标识类型（最多 32 种）
```

**类比**：快递包裹。标签（NAL 头）告诉你是 SPS 还是 I 帧还是 P 帧，内容物（载荷）就是具体数据。

**NAL 类型表**：

| NAL 类型值 | 十六进制 | 名称 | 含义 |
|:---:|:---:|------|------|
| 1 | 0x61 | 非 IDR 切片 | **P 帧** |
| 5 | 0x65 | IDR 切片 | **I 帧**（关键帧） |
| 7 | 0x67 | SPS | 序列参数集：宽高、Profile、Level |
| 8 | 0x68 | PPS | 图像参数集：熵编码方式、量化参数 |

#### 1.7.2 两种包装方式（NAL 内容本身不变）

**你的纠正（关于我之前的不严谨表述）**："意思是 NAL 头也可能不含分隔标记" → "但是他们（Annex-B 和 avcC）都叫 NAL" → "那你之前跟我说 NAL 不严谨啊" → "那 NAL 是只包含[NAL头]+[数据]"

**我的认错**：你全部说对了。我之前把"NAL"、"NAL 单元"、"NAL 的包装方式"三个概念混着用。

**严谨定义**：

```
NAL 头    = 1 字节，标识类型（SPS/PPS/I 帧/P 帧）
NAL 单元  = NAL 头 + 载荷数据（不包含任何分隔标记）
Annex-B  = 用 00 00 00 01 起始码包在 NAL 单元外面的格式
avcC     = 用 4 字节长度前缀包在 NAL 单元外面的格式
```

| | Annex-B | avcC |
|------|------|------|
| 分隔方式 | `00 00 00 01` 起始码 | 4 字节长度前缀 |
| 适用场景 | 裸流文件(.h264)、直播推流、实时传输 | MP4、FLV、RTSP 摄像头 |
| 优点 | 丢了数据能恢复（扫描下一个起始码） | 解析快，不需要扫描字节 |
| 缺点 | 需要防竞争字节（0x03） | 丢一个长度→后面全部乱 |
| NAL 数据变了吗？ | **没变** | **没变** |

**你的代码里怎么体现**：摄像头输出 avcC 格式 → `h264parse` 换包装（长度前缀→起始码）→ MPP 解码器收到 Annex-B 格式。

#### 1.7.3 avcC 格式的实际数据（十六进制）

**你的提问**：（1）能否提供 avcC 格式的实际十六进制数据示例？（2）十六进制数值如 00 00 00 1C 应如何换算为十进制？

**十六进制计算教学**：

十六进制用 0-9 + A-F 表示 16 个数字（A=10, B=11, C=12, D=13, E=14, F=15）。

心算方法：**左位×16 + 右位**（和十进制"左位×10+右位"一个道理）。

```
1C = 1×16 + 12 = 28
1F = 1×16 + 15 = 31
FF = 15×16 + 15 = 255
1F40 = 1×4096 + 15×256 + 4×16 + 0 = 4096+3840+64 = 8000
```

**实际 avcC 数据**（海康摄像头 SPS + PPS + IDR）：

```
00 00 00 1C 67 64 00 1E AC D9 ...   ← SPS（28 字节）
    ↑ 长度=1C=28  ↑ NAL=67(SPS)  ↑ Profile=High(0x64), Level=3.0(0x1E)

00 00 00 04 68 EE 3C 80             ← PPS（4 字节）
    ↑ 长度=04=4  ↑ NAL=68(PPS)

00 00 1F 40 65 88 84 00 FF FE ...   ← IDR 帧（8000 字节）
    ↑ 长度=1F40=8000  ↑ NAL=65(IDR)
```

**同一个数据用 Annex-B 格式**（只换包装，NAL 一个字节没改）：

```
00 00 00 01 67 64 00 1E AC D9 ...   ← 起始码替代了长度前缀
00 00 00 01 68 EE 3C 80
00 00 00 01 65 88 84 00 FF FE ...
```

### 1.8 SPS 和 PPS

#### 1.8.1 它们是什么

**SPS（Sequence Parameter Set，序列参数集）**：整个视频序列的全局参数，从头到尾不变。

```
Profile = High（0x64）— 支持 CABAC + 8×8 变换
Level   = 3.0（0x1E）— 最大 720×576@30fps
分辨率   = 704×576
色度格式 = 4:2:0（NV12 的采样方式）
```

**PPS（Picture Parameter Set，图像参数集）**：每帧的解码参数。

```
熵编码方式：CABAC
量化参数初始值
参考帧数量
```

**类比**：SPS = 一本书的开本（A4/B5），PPS = 字体和行间距。没有 SPS → 不知道画面多大，解码器无法启动；没有 PPS → 不知道用什么方式解读数据，解码失败。

**SPS 和 PPS 必须在 I 帧之前到达解码器。** 没有它们，就算收到 I 帧也是废的。

**代码体现**：`ffmpeg_demux.c` 里的 `extradata` 就是 SPS+PPS（avcC 格式），`d->width`、`d->height` 都从 SPS 解析出来的。

### 1.9 RTP 分包

#### 1.9.1 为什么需要

以太网 MTU = 1500 字节，一帧 H.264（8KB）超限，必须拆。不管你是传视频、打电话还是直播，数据都要经过以太网，链路层死规定一包最多 1500 字节。减 RTP 头 12 字节 = 实际每包约 1400 字节可用。

#### 1.9.2 三种方式

| 方式 | 场景 | 做法 |
|------|------|------|
| Single NAL | NAL ≤ 1400 字节（如 SPS 28B、PPS 4B） | 一个 RTP 包装一个完整 NAL |
| FU-A 分片 | NAL > 1400 字节（如 IDR 8000B、P 帧 3000B） | 切成多片，FU-A 头标记开始/中间/结束 |
| STAP-A 聚合 | 多个极小 NAL | 几个 NAL 合成一个包 |

#### 1.9.3 RTP 头关键字段

| 字段 | 长度 | 含义 |
|------|:---:|------|
| V | 2 bit | 版本，永远是 2 |
| M (Marker) | 1 bit | 帧结束标志。一帧最后一个包设 1 |
| PT (Payload Type) | 7 bit | 载荷类型。96 = H.264（在 SDP 里约定） |
| 序列号(seq) | 16 bit | 初始值随机，每发一个包 +1。接收方靠它排序和检测丢包 |
| 时间戳(ts) | 32 bit | 一帧的所有分片包时间戳相同。下一帧 ts = 上一帧 + 帧间隔 |

#### 1.9.4 FU-A 头的 start/end 位和 Marker 位的区别

```
FU-A 的 S/E 位：NAL 层，"这一片的开始/结束"
RTP 的 M 位：RTP 层，"这一帧的最后一个包"

通常同一帧最后一个包同时设 M=1 和 E=1。
```

#### 1.9.5 你的摄像头的分包情况

```
IDR 帧（8000B）→ 方式 B（FU-A）：切成 6 个 RTP 包
P 帧（2000-5000B）→ 方式 B（FU-A）：切成 2-4 个 RTP 包
SPS（28B）+ PPS（4B）→ 方式 A（Single NAL）：各 1 个 RTP 包
```

你的板子收到后，`rtph264depay` 按 seq 排序、确认 ts 相同、撕掉 RTP 头 + FU-A 头、拼回完整 NAL。

## 2. 模块 1：RTSP 拉流 + RTP 拼包

### 2.1 摄像头本身不输出"RTSP 流"

**你的纠正**：摄像头本身并不持续输出所谓的"RTSP 流"——RTSP 只是摄像头内部 Linux 系统上运行的一个服务程序，监听 TCP 554 端口，等待客户端主动连接。对吗？

**澄清**：RTSP 里的角色是反直觉的：

所以 RTSP 命令（DESCRIBE/SETUP/PLAY）都是板子发出的，摄像头回复。RTP 视频数据才是摄像头→板子方向。

### 2.3 RTSP 协议定位

**你的问题**："rtsp 也是实时传输协议吗？" + "你就说面试时候说他是什么类型的协议。"

**回答**：**应用层流媒体控制协议。**

```
RTSP = 流的遥控器（播放/暂停/停止）——管控制
RTP  = 流的搬运工（传音视频数据）——管数据
RTCP = 搬运工的回执单（丢包率、延迟统计）——管质量
```

虽然名字里带 "Real Time"，但它不传实时数据，真正的实时数据由 RTP 负责。面试：**"RTSP 是应用层流媒体控制协议，基于 TCP，文本协议，类似 HTTP，负责播放/暂停/停止控制，不传数据。数据传输由 RTP 完成。"**

### 2.4 RTSP 建立会话（三次请求-响应）

**你的提问**：RTSP 建立会话的完整信令交互是否算四次握手（包含 TEARDOWN）？

**纠正和确认**：不算四次。TEARDOWN 是拆除会话，不属于握手。建立会话是三次请求-响应（共 6 条消息），有些实现会先发 OPTIONS 探测 → 可能四次。

```
板子(客户端)                                   摄像头(服务器)
    │                                              │
①   │—— DESCRIBE rtsp://192.168.50.54/stream1 ——→│
    │   CSeq: 1                                    │
    │←—— 200 OK + SDP ──────────────────────────│
    │   Content-Type: application/sdp              │
    │   m=video 0 RTP/AVP 96                       │  ← 视频轨
    │   a=rtpmap:96 H264/90000                     │  ← H.264
    │   a=framesize:96 704-576                     │  ← 分辨率
    │                                              │
②   │—— SETUP ─────────────────────────────────→│
    │   Transport: RTP/AVP;unicast;                │
    │   client_port=50000-50001                    │  数据口 + 反馈口
    │←—— 200 OK + Session=12345 ────────────────│
    │   server_port=60000-60001                    │
    │                                              │
③   │—— PLAY ──────────────────────────────────→│
    │   Session: 12345                             │
    │←—— 200 OK ────────────────────────────────│
    │←—— RTP 数据包开始涌入 (seq=0,ts=...) ──────│
    │                                              │
④   │—— TEARDOWN ──────────────────────────────→│ ← 拆除，非握手
```

**SDP（Session Description Protocol）**：DESCRIBE 的返回内容，告诉客户端流的基本信息。`m=video 0 RTP/AVP 96` = 视频轨，`a=rtpmap:96 H264/90000` = H.264 编码，`a=framesize:96 704-576` = 分辨率。

**CSeq**：请求序号，每个请求递增，服务器回复时原样带回。用来匹配请求-响应对。跟 RTP 的 seq 是两码事。

**为什么 SETUP 指定两个端口？** RTP 数据走偶数口（50000），RTCP 反馈走奇数口（50001）。标准惯例。

### 2.5 RTSP 和 SIP 的关系

**你的问题**："我怎么感觉 rtsp 和 sip 这么像啊。"

**回答**：**它们同源。** 两个协议都是 Henning Schulzrinne 参与设计的，都借鉴了 HTTP 的文本风格。

```
HTTP (1996)
  ├── RTSP (1998) ← 流媒体控制
  └── SIP  (2002) ← 通信会话建立
```

长得像：都是文本协议（方法+头部+CSeq）、都用 SDP 描述媒体、信令和数据分离（都是 RTP 传媒体）。

| | RTSP | SIP |
|------|------|------|
| 目的 | 控制流媒体服务器（有录像，遥控播放） | 建立双方通信会话（两个人对等通话） |
| 谁发起 | 客户端主动找服务器 | 主叫找被叫，被叫可能不在线 |
| 会话 | DESCRIBE→SETUP→PLAY | INVITE→180→200 OK→ACK |
| 状态 | Session ID | Dialog（From tag + To tag + Call-ID） |
| 场景 | 监控预览、VOD 点播 | 电话、视频会议、GB/T 28181 国标 |

### 2.6 ONVIF 和这个项目的关系

**你的问题**："onfive 协议呢，我这个硬解码有用到吗？" → "用了 onvif 不用管传输数据的协议了吗，我同事说他只是用 udp 来找设备，然后用 onvif 协议联合 rtsp 去做的项目。"

#### 2.6.1 ONVIF 是什么

ONVIF 不是网络传输协议，是**安防行业标准**（基于 SOAP/HTTP，XML 通信），让不同厂家的摄像头和 NVR 能互相兼容。

#### 2.6.2 协议 vs 标准

**你的问题**："应用层标准和协议的区别。"

```
协议（Protocol）：通信双方约定的数据格式和交互顺序（具体可编码实现）。
标准（Standard）：一套完整的规范体系，含多个协议 + 数据模型 + 行为定义 + 合规要求。

协议 = "红灯停、绿灯行"（具体可编码进自动驾驶）
标准 = 整本《道路交通安全法》（含红绿灯 + 限速 + 酒驾 + 牌照...）

ONVIF 是标准，RTSP 是它引用的协议之一。
```

#### 2.6.3 你同事的项目流程

```
① WS-Discovery（UDP 组播，端口 3702）→ 发现摄像头："谁在？"→ 摄像头回复 IP
② ONVIF（HTTP+SOAP，端口 80）→ "把 RTSP 地址给我"→ 回复 URL
③ RTSP + RTP → 拉流（和你现在一模一样）
```

**你的项目没用 ONVIF**——你只有 1 个摄像头，IP 和 RTSP 地址自己知道，直接硬编码在 `config.ini` 里：

```c

```

**你的追问**：经确认，ONVIF 只负责设备发现和获取 RTSP 地址，实际的视频流传输仍然需要另外通过 RTSP+RTP 来完成？ONVIF 停手之后，RTSP+RTP 接棒。ONVIF 只帮你找到 `rtsp://...` 这行字，拿到了就没用了。

### 2.7 TCP vs UDP 在视频传输中的选择

**你的知识**："tcp 和 udp 我只知道 tcp 可靠因为有 ack 响应，中断之后能够知道从哪个中断开始重新传输，而 udp 只需要知道地址和端口就可以传输，而且不可靠其他我就不知道了。"

**补充**：

| | TCP | UDP |
|------|------|------|
| 连接 | 需要三次握手 | 不需要，直接发 |
| 可靠性 | ACK 确认 + 超时重传 | 不确认，丢了就丢了 |
| 顺序 | 严格保序（头阻塞问题） | 不保序 |
| 速率 | 拥塞控制，丢包就降速 | 无控制，全速发 |
| 头部开销 | 20 字节 | 8 字节 |
| 场景 | 文件传输、网页、邮件 | 直播、视频通话、DNS |

**TCP 对视频不友好的原因**：
1. **头阻塞**：丢了一个包，后面的包都扣着，必须等重传。
2. **拥塞控制**：TCP 发现丢包就判断"网络堵了"，主动降速且不回头。视频场景可能只是无线闪了一下，网络其实不堵。

**UDP 为什么适合视频**：丢包不管，继续发。丢了几个包→画面花一下→下一帧 I 帧到→恢复。不会降速，不会越来也卡。代价是自己处理丢包。

**你的项目为什么选 TCP**：局域网直连，丢包率极低，TCP 的缺点体现不出来。但 UDP 被很多防火墙拦——默认先试 UDP → 被拦 → 等 5-10 秒超时 → 回退 TCP。`protocols=4` 跳过试探直接 TCP，秒连。

**你同事的超时丢弃策略**：丢包后设 X 毫秒超时→超时了就丢帧→跳到下一个 I 帧重新开始。能缓解延迟累积，但不能根治 TCP 的头阻塞和拥塞控制问题。局域网环境可以接受，公网 4G 还是 UDP 更好。

### 2.9 TCP 承载 RTP（"TCP 交织"）

你的 `protocols=4` 就是 RTP over TCP。同一个 TCP 554 端口上混传 RTSP 命令 + RTP 数据：

```
┌───────┬──────────┬───────────────┬──────────┐
│ $(0x24)│ 通道号(1B)│ 长度(2B,大端) │ RTP 数据  │
└───────┴──────────┴───────────────┴──────────┘
```

用 `$` 字符和通道号区分 RTSP 命令和 RTP 数据。面试可能问优缺点：优点不丢包、穿防火墙简单；缺点 TCP 拥塞控制引入额外延迟。

## 3. 模块 2：H.264 码流结构

### 3.1 完整数据流总结（至此为止）

```
摄像头内部：
光 → CMOS → Bayer RAW → ISP(去马赛克→RGB→白平衡→降噪→锐化)
→ RGB→YUV NV12(亮色分离→色度降采样4:2:0，600KB)
→ H.264编码器(I帧完整画面+P帧预测，平均8KB/帧)
→ RTP分包(FU-A切6片，每片~1400字节，贴序号+时间戳)
→ 网口发出(RTSP信令走TCP 554，RTP数据走TCP/UDP)

板子端（已学部分）：
网口收到 → rtspsrc(DESCRIBE→SETUP→PLAY握手，latency缓冲)
→ rtph264depay(按seq排序→撕RTP头→拼回完整NAL)
→ h264parse(avcC→Annex-B，换包装纸)

板子端（待学部分）：
→ mppvideodec(MPP硬件解码，H.264→NV12)
→ videoconvert(RGA硬件 NV12→RGB+缩放)
→ fbdevsink(写入/dev/fb0显存)
→ MIPI LCD屏幕
```

### 3.2 面试常考速记

- **"为什么摄像头输出 YUV 不是 RGB？"** → 色度降采样省 50% 带宽，H.264 在 YUV 上编码效率更高。
- **"NV12 一帧多大？"** → 704×576 的 Y 平面 405,504 + UV 平面 202,752 = 608,256 字节 ≈ 600KB。
- **"h264parse 做什么？"** → 换包装纸，avcC（长度前缀）→ Annex-B（起始码），NAL 内容不变。
- **"split_parse=1 什么意思？"** → MPP 内部自动按 00 00 00 01 起始码拆分 NAL。设 0 要你自己拆。
- **"protocols=4 为什么不是字符串？"** → GFlags 类型，GST_RTSP_LOWER_TRANS_TCP = 0x04。
- **"I 帧间隔 15 帧，网络断了 7 帧错过 I 帧，后面 P 帧到达会发生什么？"** → 全挂。P 帧依赖链断裂，等到下一个 I 帧（最多等 1 秒）才能恢复。
- **"RTSP 和 SIP 什么关系？"** → 同源，都是 HTTP 的衍生。RTSP 遥控服务器，SIP 建立双方通话。
- **"ONVIF 是协议还是标准？"** → 标准。引用 WS-Discovery + SOAP/HTTP + RTSP 等多个协议。
- **"你的 RTSP 图为什么箭头指向摄像头？"** → 摄像头是服务器（等着被连），板子是客户端（主动连），所以命令是板子→摄像头。

## 4. 模块 3：MPP 硬件解码

### 4.1 什么是硬件解码

**解码** = 把压缩的 H.264 码流变回原始像素（NV12）。

| | 软件解码（CPU） | 硬件解码（VPU） |
|------|------|------|
| 做法 | CPU 逐条执行解码算法 | 芯片内专用解码电路（VPU） |
| 704×576 耗时 | ~20-50ms/帧 | ~1-5ms/帧 |
| CPU 占用 | 50-80% | <1% |
| 功耗 | 高 | 低 |

**类比**：软件解码 = 你手算 1000 道题；硬件解码 = 把题扔进计算器，按"="，拿结果。

---

### 4.2 MPP 的异步解码模型

MPP（Media Process Platform）是 Rockchip 的硬件编解码框架。它采用**异步模式**——投喂和取果是两步，中间有时间差。

```
你的程序                        MPP 硬件
   │                              │
①  │── put_packet(帧数据) ──────→│  "这帧交给你"
   │   函数立刻返回（不等结果）    │  数据进硬件队列，开始解码
   │                              │
②  │── get_frame() ────────────→│  "解好了没？"
   │←── 没解好/超时 ────────────│  重试（最多 30 次）
   │                              │
③  │── get_frame() ────────────→│
   │←── NV12 帧 ────────────────│  解好了！拿到 YUV 数据
   │                              │
④  │  显示/处理这帧...            │
   │  frame_deinit（释放） ─────→│  归还 buffer
```

---

### 4.3 put_packet 失败不是丢帧——是重试

**盘问问题**：I 帧特别大，硬件解了 80ms。期间你又投了 2 个 P 帧。put_packet 会发生什么？

**你的回答**："会丢失 P 帧后卡死，一直等到下一个 I 帧才开始继续解码。"

**纠正**：put_packet 返回的是错误码（队列满），**不是丢了数据**。你的帧还在你手里，代码要做的是 `sleep(1ms)` 再重试：

```c
// mpp_dec.c 里的重试逻辑
int retry = 0;
while (mpi->decode_put_packet(ctx, packet) != 0) {
    usleep(1000);     // 等 1ms
    if (++retry > MAX_RETRY_PKT) break;
}
```

等 I 帧解完（80ms 后），队列释放，重试中的 P 帧会被收进去正常解码。**不需要等"下一个 I 帧"**——它们依赖的 I 帧此时已经解完了，就放在已解码帧缓冲区（DPB）里。

---

### 4.4 为什么需要外部分配 Buffer Group

**硬件解码器不能直接用 `malloc` 分配的内存**——它需要 DMA buffer（物理连续内存）。

```
CPU 虚拟地址：malloc → 0x7f12345678（物理内存可能分散在多处，靠 MMU 拼成连续）
硬件 DMA：    直接操作物理地址读/写像素、必须物理连续
```

**外部分配的流程**（你的 `mpp_dec.c`）：

```c
// ① 向内核申请一批 DMA buffer
mpp_buffer_group_get_internal(&grp, MPP_BUFFER_TYPE_DRM);   // 优先 DRM
// 失败回退 ION
mpp_buffer_group_get_internal(&grp, MPP_BUFFER_TYPE_ION);

// ② 设定每个 buffer 大小和数量
mpp_buffer_group_limit_config(grp, buf_size, 24);   // 608KB × 24 ≈ 14.6MB

// ③ 告诉 MPP："用我这批 buffer，别自己分配"
mpi->control(ctx, MPP_DEC_SET_EXT_BUF_GROUP, grp);
```

**为什么选 24 个？**

Buffer 被两端消耗：MPP 内部保留参考帧（DPB ≤ 5 个，H.264 High Profile）+ 显示端未释放的帧（≤ 6 个）。(5+6)×2 ≈ 22，取整 24——这是 MPP 官方 demo（`mpi_dec_test.c`）的经验值。

**如果 buffer 不够（比如设 4 个）**：解码器等空闲 buffer 写结果、显示端等解码器出帧、互相等 → **死锁**。不是溢出，是资源耗尽。

**如果设太大（100 个）**：浪费。100 × 608KB = 60.8MB，每个都是 DMA 物理连续内存。

### 4.5 info_change：分辨率变了怎么办

H.264 流中 SPS 的分辨率可能中途变化（比如摄像头被远程改了配置）。

```
正常：SPS 说 704×576 → buffer = 608KB
变化：新 SPS 说 1920×1080 → buffer 需要 3.1MB

旧的 608KB buffer 装不下！
→ get_frame 返回 info_change 标志（而不是正常帧）
→ 你必须：读新宽高 → 释放旧 buffer group → 按新大小申请 → SET_INFO_CHANGE_READY
```

你的 `mpp_dec.c` 里 `handle_info_change` 就是这个流程。GStreamer 的 `mppvideodec` 插件内部自动处理了，你用 GStreamer 时感知不到。

## 5. 模块 4：NV12 颜色空间 + RGA 格式转换

### 5.1 NV12 内存布局（深度版）

一张 704×576 的 NV12 帧在内存中长这样：

```
偏移 0 ────────────────────────────── 偏移 405,503
       │ Y₀ Y₁ Y₂ ... Y₇₀₃                    │
       │ Y₇₀₄ ...                              │  ← Y 平面，共 576 行
       │ Y₄₀₅₅₀₃                              │
───────┼────────────────────────────────────────┼── 偏移 405,504
       │ U₀ V₀ U₁ V₁ ... U₃₅₁ V₃₅₁           │  ← UV 交错平面
       │ ...                                    │     共 288 行
───────┴────────────────────────────────────────┴── 偏移 608,255

Y 平面  = 704 × 576     = 405,504 字节
UV 平面 = 352 × 288 × 2 = 202,752 字节（每 4 像素共用 1 对 UV）
总大小  = 608,256 字节  ≈ 600KB
```

---

### 5.2 stride — 模块 4 最大的坑

**stride（步幅）= 一行在内存中实际占用的字节数，不等于 width。**

```
width = 704（实际像素宽度）
stride = 704 向上对齐到 16 → 704（刚好对齐，stride=width）

但如果 width = 710：
stride = 720（对齐到 16）

Y 每行多了 10 字节填充，共 576 行 → 多了 5,760 字节
```

**UV 平面起止计算依赖于 stride**：

```
UV 起始地址 = Y 首地址 + stride × height
            = Y + 720 × 576 = Y + 414,720   ← 正确的

如果你硬编码 UV = Y + 704 × 576 = Y + 405,504：
→ 偏了 9,216 字节
→ 读到的 "UV" 其实是 Y 平面尾部的亮度值
→ 色度错乱
```

**盘问：wstride 错 → 什么现象？**

| 你的回答 | 正确？ |
|------|:---:|
| "静默出 bug，花屏" | ✅ |
| "画面上下错位，像横切一刀" | ❌ 那是 hstride 错的现象 |
| "整体偏绿或偏紫" | ⚠️ 不固定 |

**答案**：色偏的**具体颜色不固定**，取决于偏移处像素的亮度值。

```
偏移处 Y 值 ≈ 128 → UV 接近零点 → 无色偏（看不出来！）
偏移处 Y 值 > 128  → UV 为正     → 偏紫红
偏移处 Y 值 < 128  → UV 为负     → 偏绿蓝

最危险的情况：灰度场景完全看不出 bug，换场景才暴露。
```

---

### 5.3 wstride、hstride、width、height 总结

| 参数 | 设错后果 | 现象 |
|------|------|------|
| **wstride**（Y 一行字节数） | UV 起偏（在 Y 平面内） | 整体偏绿/偏紫/无色偏（取决于画面） |
| **hstride**（Y 平面行数） | UV 起偏（越界到不同行） | 画面横切一刀，色度断层 |
| **width/height**（有效像素） | 缩放比例不对 | 画面拉伸/压扁 |

### 5.4 BT.601 转换公式

你的 `fbdev.c` 里手写的 CPU 软转换：

```c
int R = (298 * (Y-16) + 409 * (V-128) + 128) >> 8;
int G = (298 * (Y-16) - 100 * (U-128) - 208 * (V-128) + 128) >> 8;
int B = (298 * (Y-16) + 516 * (U-128) + 128) >> 8;
```

Y 范围 16~235（电视标准），UV 范围 16~240（128 为零点）。298、409、100 等是 BT.601 标准矩阵的定点数近似。

---

### 5.5 RGA — 硬件加速器

**RGA（2D 图形加速器）**是 RV1126 中**独立的硬件模块**——和 MPP 是两块不同的硅片区域，走不同的总线。

```
RGA 内部流水线：
源 DMA 读(NV12) → 格式转换(YUV→RGB, BT.601) → 缩放(704→720, 576→1280) → DMA 写(RGB)

一次调用完成，耗时 <1ms，CPU 零占用。
```

**CPU 软转换对比**：每帧 40 万像素 × 9 次运算 = 360 万次/帧 × 15fps = 5400 万次/秒 → ARM A7 50%+ 占用。

### 5.6 mmuFlag 和 IOMMU

```c
src.mmuFlag = 1;   // 告诉 RGA："我传的是虚拟地址，你用 IOMMU 翻译成物理地址"
```

**如果内核没开 IOMMU**（一些 Buildroot 默认关闭）：
- RGA 尝试翻译 → 失败
- `c_RkRgaBlit` **返回非零**（不崩溃、不段错误、不花屏）
- 你的代码：`if (p_RkRgaBlit(...)) { return -1; }` → 返回 -1
- `fb_show_nv12`：RGA 失败 → 走 CPU 软转换

**盘问问题**：mmuFlag=1，内核没开 IOMMU，会怎样？

**你的回答**："不知道。"

**答案**：blit 返回失败 → 代码走到 CPU 回退路径。画面正常，帧率暴跌（15fps → 2-3fps）。你的代码设计保证了**不会崩溃，不会花屏**——这是工程上的容错考虑。

### 5.7 三种花屏的根因对照

| 现象 | 根因 | 机制 |
|------|------|------|
| A 随机彩色噪点/雪花 | 指针指向已释放/未初始化内存 | 读到了完全不相关的垃圾数据 |
| B 整体偏绿/偏紫 | wstride 错配，UV 偏移到 Y 平面内 | UV 被 Y 值替代，色度错乱 |
| C 横切一刀 | hstride 错配，UV 偏移越界到其他行 | UV 读到不同行的 Y 数据，产生断层 |

A 最危险——是**未定义行为**，可能随机段错误。

---

### 5.8 RGA 面试速记

- **"RGA 做什么？"** → 硬件 DMA + BT.601 公式 + 缩放，一次 blit 完成，CPU 零占用。
- **"mmuFlag=1 什么意思？"** → RGA 用 IOMMU 翻译虚拟地址。无 IOMMU 时 blit 返回失败，代码自动回退 CPU。
- **"stride 错了什么现象？"** → 色度整体偏移（偏绿/偏紫/无异常），具体颜色取决于偏移处的像素亮度。
- **"你们的 videoconvert 在 RV1126 上走什么硬件？"** → RGA。如果 RGA 不可用（无 librga.so），自动回退 CPU 软转换，不崩溃。
- **"花屏有三种，怎么区分？"** → 随机噪点 = 野指针；偏色 = wstride 错；横切 = hstride 错。

## 6. 模块 5：Linux 显示框架（fbdev vs DRM）

### 6.1 屏幕到底怎么亮的（通用概念）

不管你用什么操作系统、什么硬件、什么显示接口，让屏幕亮起来永远只有**一种方式**：

**显示器 = 一块物理内存，被硬件电路持续扫描，把内存里的像素值变成屏幕上的光点。**

```
程序做的事：把 RGB 像素值写入那块内存
硬件做的事：持续扫描那块内存 → 生成时序信号（行同步、场同步）→ MIPI/LVDS/HDMI 线 → 屏幕亮了
```

CRTC（显示控制器）是一个硬件模块，在后台不停地重复：从显存起始地址开始 → 一行一行读像素 → 生成信号发给屏幕。60Hz = 每秒 60 遍。**你的程序只做一件事：把像素写进显存。**

---

### 6.2 四种显示方式

#### 方式 A：直接写物理地址（裸机/单片机）

```
你知道显存物理地址是 0x40000000
→ *(uint32_t*)0x40000000 = 0x00FF0000; // 左上角红
优点：极简，不要操作系统
缺点：不通用，多程序互踩
```

#### 方式 B：fbdev（Linux 传统帧缓冲）← 你的项目用

```
内核驱动接管显存，通过 /dev/fb0 暴露
→ open → ioctl 获取参数 → mmap 映射 → 写数据
优点：不需知道物理地址，跨硬件兼容
缺点：独占（多程序互踩），无多图层、无 vsync
```

#### 方式 C：DRM/KMS（Linux 现代显示框架）

```
内核驱动管理显示资源：CRTC、Encoder、Connector、Plane
→ 每个程序申请自己的 Plane（图层）
→ 内核把多个图层合成 → 发给屏幕
优点：多程序共存、多图层叠加、vsync 同步、GPU 渲染
缺点：代码量 3-4 倍于 fbdev
```

#### 方式 D：Wayland/X11（桌面合成器）

```
应用程序 → 告诉合成器 "我要画窗口"
合成器 → 收集所有窗口 → 合成一张 → 通过 DRM 显示
（Weston 就是板子上跑的 Wayland 合成器）
优点：多窗口、拖拽、写桌面应用的标配
缺点：嵌入式太重，引入额外延迟
```

**方式 C 和 D 的区别**：不在同一层。DRM 是内核驱动（管硬件），Wayland 是用户态合成器（管窗口）。Wayland 底层用的就是 DRM。

```
Qt 程序 → Wayland/Weston（合成器："把所有窗口叠成一张图"）
              ↓
         DRM/KMS（内核驱动："把图送到 CRTC，让屏幕显示"）
              ↓
         硬件（CRTC、MIPI DSI）
```

**全屏播放不需要合成器，自己直接调 DRM（或 fbdev）更快，少一层延迟。**

---

### 6.3 fbdev：白板模型——内存布局

**你的代码做了什么**（`fbdev.c`）：

```c
// ① 打开设备
int fd = open("/dev/fb0", O_RDWR);

// ② 获取屏幕参数
struct fb_var_screeninfo vi;
ioctl(fd, FBIOGET_VSCREENINFO, &vi);
// vi.xres = 720, vi.yres = 1280, vi.bits_per_pixel = 32

// ③ 获取显存信息
struct fb_fix_screeninfo fi;
ioctl(fd, FBIOGET_FSCREENINFO, &fi);
// fi.smem_len = 3,686,400 (显存总大小)
// fi.line_length = 2,880 (一行多少字节)

// ④ mmap 映射显存到用户态
void *fb_mem = mmap(NULL, fi.smem_len, PROT_READ | PROT_WRITE,
                    MAP_SHARED, fd, 0);
// 现在你往 fb_mem 写 = 往物理显存写

// ⑤ 写一帧：back buffer → 显存
memcpy(f->mem, f->back, f->scr_size);
```

**三个角色分工**：

```
硬件（CRTC）→ 决定 "我从哪个物理地址开始扫描"（设备树里定义）
内核驱动   → 分配管理这块物理内存，暴露成 /dev/fb0
你的程序   → 通过 mmap 拿到映射指针，写像素数据
```

**显存起始地址不是你 malloc 的，是硬件+内核决定的。mmap 拿到的只是"代金券"（虚拟地址映射）。**

---

### 6.4 为什么每像素 4 字节

**你的第一个问题**："为啥一个像素是 4 字节？"

| 格式 | 每像素 | 例子（红色） |
|------|:---:|------|
| RGB565 | 2 字节 | 5bit 红+6bit 绿+5bit 蓝 |
| RGB888 | 3 字节 | FF 00 00（但内存不对齐） |
| **ARGB8888** | **4 字节** | 0x00FF0000（A=00, R=FF, G=00, B=00） |

32 位 CPU 一次读 4 字节最快。3 字节 RGB 会跨边界，多一次内存操作。所以硬件普遍用 4 字节。

`vi.bits_per_pixel = 32` → 每像素 4 字节。

---

### 6.5 line_length 和 width 的关系（显示端也有对齐）

**你的提问**：line_length 参数是否可以在代码中自行设定？

**不是。line_length 是内核驱动返回的，你只能读，不能改。** 谁决定它？CRTC 硬件——它要求每行起始地址对齐到 64 字节（Cache line 大小）。

```
width × 4 = 720 × 4 = 2,880 → 恰好是 64 的倍数（2,880÷64=45）
                              → line_length = 2,880（无填充）

如果 width = 710（不是 64 的倍数）：
  → 710×4 = 2,840 → 2,840÷64 = 44.375 → 不对齐
  → ALIGN(2840, 64) = 2,944 → line_length = 2,944
  → 每行多 104 字节填充
```

**类比**：墙宽 720 格，但内核砌墙时可能每行多砌几格（硬件对齐）。多出来的格子你看不到（CRTC 拍照时跳过），但不是"黑边"——黑边是分辨率不匹配导致的。

**如果 line_length > width×4，memcpy 一次性全写会怎样？**

```
back buffer：每行 2,880 字节，紧密排列（共 3,686,400 字节）
显存：每行 2,944 字节，稀疏排列（共 3,768,320 字节）

memcpy(显存, back, 3,686,400)：
  第 0 行：正确（前 2,880 字节填入了显存行 0 的前 2,880 字节）
  但显存行 0 的后 64 字节填充 → 被 back 的行 1 前 64 字节覆盖！
  行 1：被 back 的行 1 第 65~...字节覆盖 → 全乱

→ 画面斜着扭曲（不是黑边，不是花屏）
```

**正确做法——逐行拷贝**：

```c
for (int y = 0; y < height; y++)
    memcpy(f->mem + y * line_length,    // 目标：显存第 y 行开头
           f->back + y * width * 4,      // 源：back 第 y 行开头
           width * 4);                   // 只拷有效像素
```

### 6.6 为什么必须先 killall weston

**你的盘问回答**："open 会失败。"

**纠正**：很多 Linux 内核的 fbdev 驱动**不检查独占**——`open` 会成功，不报错。真正的后果：

```
Weston：每隔 16ms 往显存写一帧桌面
你的程序：每隔 66ms 往显存写一帧视频

CRTC：不知道你们在打架，照常扫描
→ 扫到一半，Weston 写了新数据 → 上半帧桌面，下半帧视频
→ 下一次扫描，你的程序写了 → Weston 又覆盖
→ 屏幕：两个画面疯狂闪烁、撕裂
```

**不是权限问题，是物理上只有一块显存。** `open` 没拦你，但不杀 Weston 就没法正常显示。

### 6.7 DRM：停车场模型（为什么不需要 killall weston）

**你的提问**：DRM/KMS（方式 C）和 Wayland/X11（方式 D）虽然都是现代显示方案，它们之间具体有什么区别？

**fbdev = 一块白板，先到先得**：一块显存，谁抢到归谁。Weston 抢到了，你再写就和它互踩。

**DRM = 停车场，每人一个车位**：内核把显存切成多个 Plane（图层），每人申请自己的专属 buffer。CRTC 不是扫一个地址，而是扫多个 Plane 再叠加：

```
Plane 2（字幕层）    ← 最上面
Plane 1（视频层）    ← 中间
Plane 0（桌面层）    ← 最底层

→ 三个画面合成一张，硬件自动做，每秒 60 次
```

所以 DRM 下不需要杀 Weston——各有各的图层，互不干扰。

| | fbdev | DRM |
|------|------|------|
| 内存 | **一块**，谁抢到归谁 | **每人一块**，硬件叠图 |
| 多程序 | ❌ 互踩 | ✅ 各自图层 |
| 为什么杀 Weston | 它霸占了唯一那块 | 不需要，各有各的图层 |

- **"mmap 映射的是什么？"** → 物理显存的用户态虚拟地址映射。你写这个地址 = 写显存，CRTC 自动扫描到屏幕。
- **"Wayland 和 DRM 什么关系？"** → Wayland 是用户态合成器（管窗口），DRM 是内核驱动（管硬件）。Wayland 底层走 DRM。

## 7. RTP 协议深度复习

### 8.1 RTP 是什么

**RTP（Real-time Transport Protocol，RFC 3550）**负责搬运音视频数据。与 RTSP 的分工：RTSP 是遥控器（播放/暂停），RTP 是搬运工（搬数据）。通常跑在 UDP 上，本项目中通过 `protocols=4` 跑在 TCP 上。

### 8.2 RTP 包头（12 字节，三个核心字段）

| 字段 | 大小 | 作用 |
|------|:---:|------|
| **序列号（sequence number）** | 16 bit | 给每个包编号（初始随机，每包 +1）。接收方靠它**排序**和**检测丢包**。 |
| **时间戳（timestamp）** | 32 bit | 采样时刻。**同一帧的所有分片包 ts 相同**，下一帧 ts 跳变（跳变量 = 帧间隔）。接收方靠它**判断哪些包属于同一帧**。 |
| **M 位（Marker bit）** | 1 bit | 帧结束标志。一帧的最后一个包 M=1。告诉接收方"这帧收完了，可以开始解码了"。 |

**为什么 M 位不可替代？**

```
如果只用 seq+ts 判断帧边界：
  → 必须等下一帧的包到达（ts 变了），才能推断上一帧已收完
  → 永远比实际慢一帧

如果有 M 位：
  → 看到 M=1 立刻知道这一帧收齐了 → 马上送去解码，不用等
  → 单包帧（SPS、PPS）和流的最后一帧也必须靠 M 位判断完整性
```

### 8.3 同一帧的包：seq 不同，ts 相同

```
一帧 IDR（切 6 包）：
  包 1: seq=100  ts=90000
  包 2: seq=101  ts=90000
  ...
  包 6: seq=105  ts=90000  M=1

下一帧 P 帧（切 3 包）：
  包 7: seq=106  ts=96000  ← ts 变了！新的一帧
  包 8: seq=107  ts=96000
  包 9: seq=108  ts=96000  M=1
```

**seq 管排序**（全局递增，不管帧边界），**ts 管分组**（同一帧不变，换帧跳变），**M 位管收尾**（告诉你"这帧齐了"）。

### 8.4 FU-A（Fragmentation Unit type A）

**通用概念**：H.264 标准（RFC 6184）定义的 NAL 分片方式。单个 NAL 超过约 1400 字节时，切成多片，每片贴 S/E 标签。

**三种分片**：FU-A（最常用）、FU-B（更严谨的防竞争版本，几乎不用）、STAP-A（多个小 NAL 合成一个包）。

**FU header 三个关键位**：S（Start）= 第一片，E（End）= 最后一片，Type = 原 NAL 类型（5=I帧，1=P帧）。

**你的项目**：摄像头用 FU-A 切大 NAL，`rtph264depay` 内部解析 S/E 位拼回完整 NAL。

### 8.5 SSRC（同步源标识）

32 位随机数，唯一标识一个媒体流的来源。**单路流场景（你的项目）**几乎没用，**多路流场景（视频会议、混流器）**靠它区分不同摄像头/麦克风的包。

### 8.6 PT / Payload Type（载荷类型）

7 bit（值域 0~127），告诉接收方包里装的什么编码。**0-95 是静态分配**（IETF 写死），**96-127 是动态协商**（通过 RTSP 的 SDP 确定含义）。PT=96 在你的会话里 = H.264，在其他会话里可能是 H.265——**PT 值本身不说明问题，必须结合 SDP 解读。**

### 8.7 你的代码中的相关参数

```c
// rtph264depay：内部按 seq 排序、按 ts 分组、按 M 断帧、解析 FU-A S/E 位
depay = gst_element_factory_make("rtph264depay", "depay");

// latency=300：jitterbuffer 缓冲 300ms，给乱序和延迟的包留时间
g_object_set(rtspsrc, "latency", 300, NULL);

// protocols=4：RTP over TCP（$ + 通道号 + 长度 + RTP 数据，与 RTSP 共用 554 端口）
g_object_set(rtspsrc, "protocols", 4, NULL);
```

### 8.8 面试速记

- **"RTP 的 seq 和 timestamp 分别干什么？"** → 序列号管排序和丢包检测。时间戳管哪几个包属于同一帧。M 位标记一帧最后一包，让接收方知道可以开始解码。
- **"FU-A 是什么？"** → H.264 的 RTP 分片方式。NAL 超 MTU 时用 FU indicator + FU header 替代原 NAL 头，S/E 位标首尾。
- **"SSRC 干什么？"** → 区分同一会话中的不同媒体源。单路流无实际作用。
- **"PT=96 一定是 H.264 吗？"** → 不一定。96-127 是动态分配，含义由 SDP 协商决定。
- **"7 个 bit 为什么是 128 个值？"** → $2^7 = 128$，值域 0~127。PT=96 是取值而非位数。

## 8. 附录：基础知识

### 8.1 十六进制速查

十六进制用 0-9 + A-F（A=10, B=11, C=12, D=13, E=14, F=15）。

计算：**左位×16 + 右位**（类似十进制 23 = 2×10 + 3）。

| Hex | 十进制 | 计算 | Hex | 十进制 | 计算 |
|:---:|:---:|------|:---:|:---:|------|
| 0A | 10 | 0×16+10 | 1C | 28 | 1×16+12 |
| 0F | 15 | 0×16+15 | 20 | 32 | 2×16+0 |
| 10 | 16 | 1×16+0 | 3F | 63 | 3×16+15 |
| 14 | 20 | 1×16+4 | FF | 255 | 15×16+15 |

多字节：`1F40` = 1×4096 + 15×256 + 4×16 + 0 = 8000。

### 8.2 握手（Handshake）的概念

**你的提问**：在计算机网络中，"握手"（Handshake）的具体含义是什么？

**回答**：通信双方在传正式数据之前，先互相确认"你是谁、我准备好了、开始吧"。两层含义：

- **传输层握手**（TCP 三次握手）：SYN → SYN+ACK → ACK。保证连接能通。
- **应用层握手**（RTSP 信令）：DESCRIBE → SETUP → PLAY。保证双方对数据格式达成一致。

生活中到处是握手：打电话时你先拨号→对方接听→"喂"→"喂，是我"→开始聊正事。

### 8.3 分辨率由什么决定

**你的提问**：项目中摄像头分辨率为 704×576（而非 1920×1080），这个分辨率是由什么因素决定的？代码能否控制？

**回答**：由硬件决定，不由代码决定。摄像头感光芯片出厂就是 704×576（PAL D1 制式）。换一个 1080P 摄像头，数据就是 1920×1080 的，代码一行不用改。GStreamer 会自动从 SDP 里读到新分辨率传给 mppvideodec。同理屏幕分辨率 720×1280 是 MIPI DSI 面板物理像素决定的，videoconvert 负责做缩放。

### 8.4 常见误解纠正

| 误解 | 纠正 |
|------|------|
| "RTSP 流 = 摄像头输出的视频流" | RTSP 只传控制命令，视频数据是 RTP 传的。RTSP 是服务程序，不是数据本身 |
| "RGB→YUV 是为了省空间" | 转换本身不省（大小一样），省空间的是后面的色度降采样 |
| "GOP=15 意思是 60fps 下 60 个 P 帧" | GOP 是帧数，不是帧率。60fps、GOP=15 = 每 0.25s 一个 I 帧 |
| "NAL 就是 Annex-B 或 avcC" | NAL 是标签+内容，Annex-B/avcC 是外面的包装纸 |
| "4 是四个协议" | `protocols=4` 是 GFlags 枚举值，GST_RTSP_LOWER_TRANS_TCP=0x04，不是数量 |

### 9.2 数据大小变迁

```
原始光信号 → RGB(1.2MB) → NV12(600KB) → H.264(8KB) → RTP碎片(×6) → NV12(600KB) → RGB加缩放(2.7MB) → 屏幕

   摄像头内部压缩 ↓150倍              网络传输 ↓6包/帧         板端解压 ↑75倍         显示放大 ↑4.5倍
```

### 9.3 三个硬件模块分工

| 硬件 | 做什么 | CPU占用 | 本项目的GStreamer元件 |
|------|------|:---:|------|
| **MPP/VPU** | H.264解压缩 | <1% | `mppvideodec` |
| **RGA** | NV12→RGB + 缩放 | 0% | `videoconvert`（内部调用） |
| **CRTC** | 显存扫描→屏幕 | 0% | `fbdevsink` → `/dev/fb0` |

### 9.4 延迟构成

```
RTSP握手       ~0.5s（一次性的）
jitterbuffer   ~300ms（latency参数）
MPP解码        ~1-5ms/帧
RGA转换        <1ms
fbdev写入      <2ms
─────────────────────
总延迟          ~300-500ms
```

瓶颈在 jitterbuffer。局域网、TCP 环境下可尝试将 latency 降到 100-150ms（前提是不丢包）。

> **光 → 压缩 150 倍变成字节 → 穿过网线 → 板子解压 → 翻译颜色 → 放大填满屏幕 → 硬件自动显示。CPU 全程几乎不干活，全是硬件在跑。**
